# Changelog

All notable changes to the Brother QL Printer App will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [4.0.0-dev] - 2026-08-05

### Breaking Changes
- **Printing is now asynchronous (print queue).** The print endpoints (`/text/print`, `/image/print`, `/qrcode/print`, `/label/text-qrcode`, `/label/text-image`, `/pdf/print`) now enqueue the job and return **immediately**. The response shape is unchanged (`{ "success": true, "job_id": "...", "message": "..." }`), but its meaning changed:
  - `success: true` now means **"queued"**, not "printed".
  - A print **failure** no longer comes back as an HTTP error on the print call: the call still returns `200`, and the failure surfaces later as the job's status (`failed`).
  - The `message` text changed (e.g. `"Print job queued"` instead of `"Text printed successfully"`).
  - *Migration:* to confirm the actual print result, poll `GET /api/v1/jobs/{job_id}` and check `status` (`done` / `failed`). Fire-and-forget clients that do not inspect the result need no change.
- **Large batches require explicit confirmation.** Any print request for **10 or more copies** must include `confirm_large_batch` (`true` for JSON endpoints, `"true"` for multipart). Without it the request is rejected with **HTTP 400** and code `CONFIRMATION_REQUIRED`.
  - *Migration:* add `confirm_large_batch: true` to requests that print 10+ copies. Requests for fewer than 10 copies are unaffected.
- **`available` no longer means "the device answered".** `POST /printers/status` now reports readiness and reachability as two separate things. `available` used to be true whenever the printer replied, so a printer with its cover open or an empty media bay came back as `available: true` beside a status line reading "Printer is stopped". A client checking the obvious boolean was told the printer was ready at the moment it could not print at all. `available` now means **nothing known prevents printing**, and the old meaning moved to the new `reachable` field. Two further fields say which question was actually settled: `state` (`ready`, `blocked`, `unknown`, `unreachable`) and `blocking_reasons`, the reported conditions as IPP keywords such as `cover-open` or `media-empty`.
  - *Migration:* a client that read `available` as "can I print right now?" needs no change and simply becomes correct. A client that read it as a reachability or monitoring signal — "is the printer on the network?" — must switch to `reachable`, or it will start reporting an open cover as an outage. The dry run's `printer_reachable` follows `reachable`, and `GET /health/printer` still returns 200/503 on reachability alone. A printer that answers but cannot print now reports `warn` with its blocking reason instead of failing: an open cover is a supply problem for a person, not an infrastructure fault for an orchestrator to restart something over.

### Added
- **USB / non-network printer support**: `usb://` and `file:///dev/usb/lpX` backends in addition to network printers; keep-alive is automatically disabled where it is not meaningful.
- **Printer status & clock**: IPP-based printer status and reachability reporting, plus a printer clock readout.
- **Health & deployment**: `GET /health` (liveness, answering `{"status": "pass", "version": …}`, overridable with `APP_VERSION`) and `GET /health/printer` (readiness) endpoints; the app now runs under gunicorn via `wsgi.py` — one worker and four threads, because keep-alive, the print queue and the relay scheduler are single-process singletons owning background threads. API-key authentication and CORS are listed under Security below.
- **Copies, cut & density options**: copies (1–100), cut modes (`each`/`end`/`none`) and density/quality options (600 dpi, HQ). Copies and cut are available directly in every compose section.
- **PDF printing**: upload a PDF, select pages, fit/fill scaling, with per-page preview (`POST /pdf/print`, `POST /pdf/preview`) and a PDF compose tab.
- **Share hand-off**: `POST /api/v1/share` (+ `GET /share/{token}`) to send a PDF or image from a phone (Apple Shortcuts / Android HTTP Shortcuts) straight into the print form.
- **True-to-print live preview**: server-rendered previews for text, QR, combined and image labels (`/text/preview`, `/qrcode/preview`, `/label/preview`, `/image/preview`), backing the instant client-side preview.
- **Optional `settings` on print/preview**: any field of `settings` (or the whole object) may be omitted. The app fills it from its saved configuration, so "print on the configured printer" needs no settings at all; fields present in the request still override.
- **Raw PNG previews**: send `Accept: image/png` to the preview endpoints to get the raw PNG bytes (with `X-Label-Width-Px` / `X-Label-Height-Px` headers) instead of the JSON data-URL wrapper.
- **Automatic text wrapping**: long text now wraps at word boundaries to fit the label (with hard-breaking of over-long words) instead of being truncated. This applies to plain text, text+QR side-by-side and QR captions, in both print and preview. On by default; disable per request with `text.wrap: false` (or `settings.text_wrap: false`).
- **Lengthwise text on continuous rolls**: text labels can now be printed along the tape instead of across it. With `settings.orientation: "lengthwise"` the roll's printable width becomes the line height and the tape grows with the message, so a long text on a narrow roll (e.g. 12 mm) comes out as one continuous, readable strip instead of a narrow column in a shrunken font. The text reads bottom-to-top when the strip is held upright; combine with `rotate: 180` for the other direction. Applies to `/text/print` and `/text/preview`; die-cut labels have a fixed size in both directions and always print `across` (the default).
- **Vertical text alignment**: `settings.vertical_alignment` (`top`, `middle` or `bottom`) positions the text block across the label's height, the counterpart to `alignment`, which positions it along the width. It matters most on die-cut labels, whose height is fixed: a 24 mm round label has a lot of vertical room, and until now the text sat in the middle of it with no way to move it. On a continuous roll it moves the text across the tape width when `orientation` is `lengthwise`; with the default `across` orientation the label grows in length to fit the text exactly, so there is no spare height to move within and the setting has no effect. Applies to `/text/print` and `/text/preview`; the default `middle` reproduces the previous behaviour.
- **Print alignment calibration**: content can land off-centre on the physical label. Die-cut registration tolerance, per-model raster offsets and media variation all push it around, and on a round label a design that is mathematically centred can print visibly off the circle. Until now the only remedy was swapping label identifiers. `settings.calibration` now holds a correction per label type, in millimetres (`"calibration": { "d24": { "x_mm": -0.5, "y_mm": 1.0 } }`), and Settings gained a **Print Alignment** dialog that runs the whole loop: print the target, look at how far it sits off-centre on the label, nudge the print the same way, print again. The target carries a ring (round media) or a frame (rectangular and continuous media) on the edge of the printable area, a millimetre scale on both axes and a caption naming the label and the offset it was printed with, so the error can be read off the label itself without a ruler. Calibration is applied **when printing only and never to the preview**: the preview stands for the label you designed, and calibration exists to make the paper match it. The calibration target is the one deliberate exception, since where the ink lands is its whole subject. Stored per medium rather than per printer, because the media is the dominant cause; an absent map or an absent key means no correction, so nothing changes for an installation that never calibrates. New endpoints `POST /api/v1/calibration/test-print` and `POST /api/v1/calibration/preview`; the test print also accepts `dry_run`, and an optional `sweep` (API only) that prints several numbered targets stepping around the current value, so the right one can be picked instead of worked out.
  - **The sideways offset moves the whole raster along the print head**, so no content is ever cut off. The travel is asymmetric, though, and bounded by how much head sits beside the loaded roll: a 24 mm round label on a QL-820NWB has roughly 37 mm of travel one way and only 3.5 mm the other. A request beyond that is clamped, and the clamp is reported rather than silently swallowed: the printed target captions itself with the offset it was really printed with, the dialog says so, and the API returns `offsets_mm`, `requested_offsets_mm`, `clamped` and `sideways_travel_mm`.
  - **Along the feed the content moves inside the label's own canvas**, because the raster starts where the feed starts and there is no equivalent lever. A large `y_mm` can therefore push content off the edge, which is logged with the amount per side; on continuous media a positive `y_mm` trims the trailing edge instead of adding a lead-in, and warns with the millimetres lost.
- **Size correction for printers that lay ink slightly large or small**: `scale` in the same calibration entry (0.95–1.05) multiplies the printed content about the centre of the label, and the calibration dialog adjusts it in percent — "smaller" and "larger" by 0.1 / 0.5 / 1 %, with the stored multiplier shown underneath as `x0.980`. It is a correction, not a zoom: the range is deliberately narrow, the canvas cannot grow, so scaling up crops at the rim (and logs it), and like the offsets it applies to prints only and never to the preview. Scale is applied before the offsets, so correcting the size does not un-correct an alignment already measured.
- **Experimental: bleed into the label's unprintable margin (`bleed_mm`)**: every die-cut label is offered smaller than it is. `brother_ql` publishes 20 mm of a 24 mm round label as printable, so about 2 mm of paper all round is unreachable by any design: the bare ring you can measure on a finished label. `bleed_mm` hands that strip back, keyed by label type, in millimetres per side. It is **off by default**, has no UI control (set it in `settings.json` or per request via the API), and unlike `calibration` it *does* show in the preview, because it changes how large the label you are designing is. Whatever is asked for is clamped to what the medium and the print head can actually give (5 mm on `d24` yields 2.03 mm, and only 1.02 mm is available on 62 mm tape on a QL-800-class printer); values above 5 mm are rejected as a wrong unit rather than a request. It is marked experimental for reasons worth reading before switching it on:
  - **It widens the label and never lengthens it, and that cannot be fixed.** Each raster line is one step of the paper feed, so extending the raster along the feed makes the media advance further per label — 284 lines instead of 236 adds about 4 mm to every d24 page — and the cutter walks off the gap between labels until the roll loses registration. This was confirmed on paper twice, the second time on a freshly seated roll, which rules out the media seating as the cause. The only feed-related command in the stream carries the medium's own margin and is packed unsigned, so the extra steps cannot be given back. Across the tape there is no such coupling: a bled job emits exactly as many raster lines as an unbled one.
  - **A bled round label is an ellipse, not a circle** — 24 × 20 mm on `d24` — and the layout follows that ellipse rather than retreating to the circle inside it, which would have handed the bleed straight back. Because the canvas is no longer square, `rotate` 90 and 270 stop working on a bled round label, exactly as they have never worked on rectangular die cuts; such a request is now refused with an explanation naming the medium and the sizes instead of an opaque failure. `rotate` 0 and 180 are unaffected.
  - **The default stays off on purpose.** The gain is 2 mm, it trades a round printable area for an oval one, and the feed half of the same idea destroys the cut. Even coverage on the smaller circle is the better default. What you opt into, on the paper: the die cut and the feed each vary by a few tenths of a millimetre, so content taken right out to the edge will show that variation from label to label, and anything overshooting the cut is printed on the liner between labels, which is visible on a black-heavy design. Bleed is for backgrounds and colour meant to run off; keep text, codes and borders inside the published area.
- **Searchable media picker**: the Label Type dropdown was 34 bare identifiers with no clue what each medium was for. It is now a picker that searches a catalogue of every supported medium — by Brother product code, identifier, size, form and description — with the results grouped into continuous rolls, die-cut labels and round labels. `DK-11218`, `dk11218`, `11218` and `DK-1218` all land on the 24 mm round label (`d24`). Both regional article numbers are indexed, since the European code doubles the leading digits and matching only one would leave half of all users finding nothing. Brother's short-side-first sizes are matched in both orders as well, so `29 x 62` finds `62x29`. An identifier covering several products lists all of their codes. Closed, the control is one line like the selects around it: the medium's name, its leading product code and a count of the rest as a small chip ("DK-22205 +11"). The description and the full list of codes appear in the open list, where there is room for them. The plain `label_size` select remains underneath as the single source of truth, so the app still works without JavaScript.
- **Copy the product code**: a button under the media picker copies the selected medium's Brother product code to the clipboard for reordering — nobody reorders a "d24"; they reorder DK-11218 — and names the code it copied, so what lands on the clipboard is never a guess. It works over plain `http` on a LAN address, where the browser clipboard API is unavailable, and says so plainly if the copy fails rather than claiming success.
- **Round media is previewed as round**: the printer receives a square raster, but the label is punched out as a circle, so the preview used to show content sitting in corners that never reach the label. The preview now draws the die cut and veils the discarded area, so ink escaping the circle fades toward the paper it will never reach. The rendered image itself is untouched: it is what goes to the printer, and the preview stays true to print.
- **The printer says which roll is loaded, and the app can show it, warn about it, or follow it.** The label type used to be something you kept in sync with the paper by hand, and getting it wrong produces a label that looks like a bug rather than like a mistake. The printer knows what is in it and says so over IPP, in the same status call the app already makes. The reading therefore costs no extra round trip and cannot be out of date. A third pill in the header names the medium, and its dot says whether that agrees with what the app is set to print for: **green** when they agree, **red** when they do not, naming the roll that is loaded and offering one button to adopt it, and **neutral** whenever nothing is loaded, the cover is open or the printer does not answer, because not knowing is not a disagreement. Clicking the pill opens the same label picker Settings uses, so changing a roll no longer means going into Settings and hunting through thirty entries. A roll change passes through cover-open and no-media on its way, sometimes for a while, so the pill keeps the last identified name rather than flapping, and re-checks itself a few seconds later. A swap therefore shows up almost at once without a second polling loop. `POST /printers/status` carries the whole reading in a new `media` block: `detected`, `detection`, `width_mm`, `length_mm`, `media_type`, `media_name`, `is_round`, `candidates`, `ambiguous`, `reason` and `matches_label_size`. A backend that cannot report media at all (USB, a kernel device, or a network printer without IPP) says so with `detection: "unsupported"` instead of guessing.
- **Three media cannot be told apart from the device, and the app deliberately refuses to guess between them.** All 15 die-cut sizes resolve to exactly one label identifier. Three continuous cases never will: `62` and `62red` are the same geometry and the printer reports the colour as `unknown`; `12` and `12+17` are one physical roll addressed two ways; and `103` and `104` differ by about a quarter of a millimetre, finer than anything the printer reports. Identification therefore returns *every* candidate the reading is consistent with, never a single pick, and says why in `reason`. This is the point of the feature rather than a shortcoming of it: `62red` is the case where a wrong guess costs you a finished, wrong label — black ink where red was wanted, on tape already through the machine — instead of an error you can read and act on. A visible question is cheaper than a bad print, so the header pill states what the printer actually knows ("62 mm continuous") rather than one of the pair, and the picker offers both with the reason attached and nothing preselected.
- **Automatically following the loaded roll** (`media_auto_switch`), with two settings that let it decide safely: `owned_media`, the media you actually have, and `media_memory`, the label type last settled on for each medium. All three are off or empty by default: every other setting changes what happens when you ask for something, while this one changes a stored setting, `label_size`, with nobody asking, so it has to be chosen rather than inherited. An ambiguous roll is resolved in a fixed order, and the first step that yields exactly one identifier wins: what was last used on this medium (`media_memory`), then the one candidate you say you own (`owned_media`), then the documented plain variant — `62` over `62red`, `12` over `12+17`, `103` over `104`. Each of those is something you told the app; none of them is a tie-break the app invented, and if none of them decides, nothing is switched and the ambiguity is surfaced exactly as the manual path already surfaces it. It never switches away from a label type that already fits what is loaded: `62red` stays `62red` on a 62 mm roll, because that is one of the things the roll can be. `owned_media` narrows without ever censoring: a roll you did not list is still read, identified and reported. A switch is announced rather than modal, held back while the picker is open, and suppressed for the current roll right after a manual choice, since a mode that undid a deliberate decision half a minute later would be worse than no mode. The server reports the decision (`media.resolution` and `media.auto_switch` on `POST /printers/status`) and the client carries it out; a status check never writes settings, so asking whether the printer is up cannot change the configuration.
- **An explicit preference decides which variant of a medium wins** (`media_preference`). Ownership was supposed to settle the three media that cannot be told apart from the device, and mostly cannot: `12`/`12+17` and `103`/`104` are one physical roll under two identifiers, so "owning both" is not a thing anyone can do, and `62`/`62red` is only settled for someone who owns the red roll and no plain one — own a black roll and a black/red roll, the ordinary case for the one medium where guessing wrong costs a finished bad label, and ownership narrows nothing. `media_preference` says it directly — "when a 62 mm roll is loaded, I mean the red one" — and is consulted **before** the memory, the owned-media list and the plain-variant default. Ahead of the memory deliberately: the memory is inferred (what happened last) and a preference is stated (what was meant), so a single contrary run on some Tuesday does not quietly repeal a standing instruction; the pick is still recorded, it simply does not outrank the instruction. Empty by default, so an installation without an entry resolves exactly as it did before, and `media.resolution.resolved_by` on `POST /printers/status` gained the value `preference`. An entry for a medium with only one variant is inert rather than rejected: it states the only thing that medium could resolve to, so it can neither change an outcome nor break one.
- **The media you own leads the picker.** Thirty entries, of which most people own three or four: those now sit at the top under "My media". "Loaded in the printer" stays above it, because that group is at most two rows and carries the note explaining an ambiguous detection, which should not sit below a personal shortlist. Each medium appears in exactly one group, and the groups narrow under search like every other group. Owning nothing produces no headings and no extra rows, so the default list is exactly as it was.
- **A manual refresh button beside the status pill**, for the moment right after changing a roll, when waiting up to thirty seconds for the next poll is the wrong answer.
- **Switching the printer's mains supply by webhook (relay power control).** A Brother QL normally powers itself up as soon as mains power returns, so the printer can be left switched off at the wall and still print on demand, with nobody walking over to press its power button. A network printer that sleeps has to be woken before it can print and left unpowered otherwise, and both ends of that can be a relay on a webhook: `turn_on` is fired when a print job arrives and the printer does not answer (the job then waits in the queue while the printer boots instead of failing), and `turn_off` once everything has wound down. It is **off by default** (`relay_webhook_enabled`), every other relay setting is inert while it is off, and `turn_off` is opt-in again on its own (`relay_webhook_turn_off_enabled`), because cutting mains power is the half of this that can go wrong. `turn_off` also requires keep-alive in `timed` mode with a non-zero duration: the turn-off moment is measured from the end of that window, and without an expiry there is no origin to measure from. The webhook body is JSON (`{"action": "turn_on", "source": "brother_ql_app", "printer_uri": …, "printer_model": …, "timestamp": …}`), and `turn_off` may use a second URL for relays that switch on the address instead of the body. If the endpoint needs a credential, it is read from the `RELAY_WEBHOOK_AUTHORIZATION` environment variable rather than stored as a setting: `GET /settings` returns the configuration verbatim to anyone who can read it, and a header that can switch mains power does not belong in that response. `GET /api/v1/printers/relay-power` reports the state, the derived timing and the last webhook, and sends nothing itself.
  - **The timing chain, and the one thing the app cannot check for you.** The printer's own auto-power-off starts counting when the keep-alive heartbeat stops, so left alone a four-hour window would give four hours *plus* the device's timer. `printer_auto_power_off_minutes` is therefore subtracted from `keep_alive_duration_seconds`, and the total comes out at exactly what was configured: with a 4 h window and a 10 min device timer the heartbeat stops at 3:50, the printer switches itself off at 4:00, and `turn_off` goes out at 4:05 — after `relay_webhook_turn_off_delay_minutes`, to a device that is already off. A duration equal to the device interval is valid and intended (the heartbeat does nothing and the hardware carries the whole window); a shorter one is refused, naming both numbers.
  - ⚠️ **This app cannot read or change the printer's built-in auto-power-off time.** The value you set here is a statement about the device, not a setting on it, and nothing verifies that the two agree. Set it to exactly what the printer's own menu shows. **If the real interval on the device is longer than the value configured here, the relay cuts mains power while the printer is still running, which can interrupt a print mid-feed and can damage the printer.** Pending work resets the clock unconditionally, so a queued or printing job can never be switched off underneath itself, and the scheduled moment is persisted, so a restart mid-window does not strand the relay in the on state. Neither of those protects against a wrong interval.
- **A relay panel in Settings.** The relay's configuration is a set of fields rather than a task, so it lives in Settings instead of a dialog of its own: off, it is two sentences and a switch; on, it unfolds in place into two columns — one per action, each with its URL and its own button to fire it — the device timer with the hazard warning inside the same field, and the timing chain in full. It opens with the point of the feature (a Brother QL powers itself up when mains power returns, so the printer can stay switched off at the wall and still print) rather than with what each setting does, states the timed keep-alive precondition where turn-off is configured, and says plainly when the fields differ from the saved file — which is also why the send buttons follow stored settings rather than typed ones: the server fires what is in the file. The warning about the printer's built-in auto-power-off is shown **before** the feature is switched on rather than after. The active tab now survives a reload (it lives in the URL hash, so it is bookmarkable and two windows stay independent).
- **The relay can be fired by hand**: `POST /api/v1/printers/relay-power/send` sends one `turn_on` or `turn_off` webhook immediately and reports the URL, the exact body, the relay's HTTP status and whether a credential went with it — so a relay can be proved to answer without queueing a print job or waiting out a four-hour window. It is called *send* rather than *test* because it really switches mains power. It requires `relay_webhook_enabled` and a URL, but deliberately **not** an armed schedule: whether the relay switches off is worth establishing before arming something that will cut power unattended. The schedule is untouched in either direction — a hand-sent `turn_off` does not clear a scheduled one, and a hand-sent `turn_on` does not arm one, because the scheduled moment is measured from the last print and a button press is not a print. The HTTP status describes the request, not the relay: a refusal, a 401 or no answer at all comes back as `200` with `success: false` and the reason, and `400` means nothing was sent. A delivery that could not be confirmed reports mains power as `unknown` rather than `off`, since the relay may well have acted before its answer failed.
- **A job says what it is doing while it waits.** A job sent to a sleeping printer switches the mains on and then waits for the device to boot and join the network, which can take minutes; from the outside that was indistinguishable from an idle queue. Every job now carries an `activity` (`switching_on`, `waiting_for_printer`, `printer_settling`, `printing`, `retrying`, or null when it is simply waiting its turn), a readable `activity_message` and the time the phase began (`activity_at`), on `GET /jobs`, `GET /jobs/{id}` and `GET /jobs/queue` alike. **`status` keeps exactly its five documented values** — the activity is a detail beside the status, not a sixth status, so no client that branches on `status` has to change. The token is stable enough to switch on; the message quotes real durations and is meant to be displayed. A gate failure clears the activity and puts the whole account in the error, because a failed job is not doing anything.
- **The queue's phases are drawn as a rail, and the current one appears in the header.** A cold start is four phases and can run to minutes, so the queue draws them as a rail — switching on, booting, settling, printing — with what is done behind the current mark and what is still to come ahead of it, so a long wait reads as a place in a sequence rather than as a stall. A retry gets no mark of its own: it is the printing step in trouble, so that mark changes colour and icon instead. Underneath, a strip carries the server's own sentence, an elapsed counter and a slow sweep, and disappears completely when nothing is underway; the row it refers to is marked and names its phase, and an unrecognised phase is shown rather than swallowed, so a phase added on the server needs no release in the UI. The same phase also appears as a pill in the header beside the printer status, with its own slow poll of `/jobs/queue` every 4.5 s that stands down whenever the queue panel is already polling faster.
- **Emphasis in text labels is actually printed** (`text_markup`, off by default). The hint under the text field has promised `**bold**` and `*italic*` since 3.0.0 and the label renderer never honoured it — it parses one tag, `<br>` — so the asterisks were set as asterisks while the browser preview showed them working, which is worse than a missing feature. Emphasis now runs through a run-based text model (`src/utils/text_markup.py`) that measuring, wrapping, auto-fit and vertical alignment all use, since every layout decision here is made from measured text. It hangs off a setting and defaults to off because of the one thing that cannot be had for free: labels have always been set in DejaVu Sans Bold, the right default on a thermal printer, which leaves nothing heavier for bold to be — so markup drops the base to the regular weight and every label set that way comes out lighter. With it off, each line is a single plain run in the face this app has always used and no existing label moves by a pixel. Applies to the text label endpoints; the QR and image layouts print the markers as typed. The live preview sends the setting with every render and only shows emphasis where the printer would honour it, and it now escapes the text it draws, which it previously wrote into the DOM as markup.
- **`tools/boot_timeline.py`**: a read-only diagnostic that measures what a printer does between mains-on and ready. It counts down so the printer is switched on at exactly t=0, then watches ICMP, tcp/9100, tcp/631 and the app's own status check in parallel, recording for each the first sighting, the point it stayed true, and how many times it dropped out — the number that justifies a settle period at all. Every wait in the relay gate is set against this measurement; a printer that boots differently can be measured the same way.
- **Dry run**: pass `dry_run: true` to any print endpoint to validate the request end-to-end (render + printer reachability) without printing or queueing. Returns `{ ok, dry_run, printer_reachable, would_print: { label_size, copies, width_px, height_px } }` — useful for endless media and CI.
- **Print queue**: all jobs are queued and printed sequentially by a single background worker. `/jobs` endpoints to list, get, cancel, reprint, delete and download a job's file, plus a Queue panel. Reprint with the same settings or re-open a job's parameters; image/PDF job files persist for `JOB_FILE_TTL_SECONDS` (default 24 h).
- **Queue controls**: pause/resume (`POST /jobs/pause`, `/jobs/resume`), an emergency stop that cancels all waiting jobs (`POST /jobs/stop`), delete a single job (`POST /jobs/{id}/delete`), clear every job (`POST /jobs/clear-all`), and a queue status endpoint (`GET /jobs/queue`).
- **Text + Image labels**: `POST /label/text-image` endpoint and compose tab to print an uploaded image and a text block side by side.
- **Large-batch confirmation guard**: any print request for 10 or more copies must include an explicit `confirm_large_batch` flag, otherwise it is rejected with HTTP 400 and the machine-readable code `CONFIRMATION_REQUIRED`. The UI confirms before submitting such a batch.
- **Dynamic keep-alive**: keep-alive can run `forever` or in a `timed` mode that keeps the printer awake only for a configurable window after each print (`keep_alive_mode`, `keep_alive_duration_seconds`), plus an always-visible keep-alive toggle in the top bar.
- **Configurable uploads**: ephemeral, configurable upload folder (`UPLOAD_FOLDER`) with TTL cleanup of staged job/share files (`JOB_FILE_TTL_SECONDS`, `SHARE_TTL_SECONDS`).
- **Demo mode**: a bundled demo layer (`src/static/js/demo.js`) lets the static UI run on GitHub Pages with mocked API data and no backend, plus a `pages.yml` deploy workflow. It activates only on a `*.github.io` host or with `?demo` in the URL, so a real installation never touches it. Its banner says both of the things a visitor needs to know: no printer is connected and every action is simulated, and the previews there are drawn in the browser because the true-to-print ones come from a backend a static host does not have — close, not identical. Web analytics for the published demo are added to the artifact by the Pages workflow from repository variables and exist nowhere in the tree, so no clone, fork or Docker image reports anything to anyone; with the variables unset the workflow says so and deploys the demo untouched. The published demo also carries the API reference as a static page at `/api/`: the Pages workflow renders `openapi.yaml` with Redoc into one self-contained file that requests nothing at run time, pinned to a fixed version rather than whatever a CDN serves that day. The demo's footer link points there, because the Swagger UI it used to point at is served by the backend and does not exist on a static host — the link went to the repository instead, which answered a different question than the one being asked.
- **Testing & tooling**: unit tests covering URI validation, the IPP client, settings, printer status, media detection, the print gate and its attempt schedule, relay power control, the multipart settings schema and text markup, plus project tooling (Dependabot, dependency audit, lint/test configuration).

### Changed
- **Every error answers in one shape.** The specification declares a single `Error` object (`code`, `message`, `details`) and four shapes were actually in circulation: our own errors used it; Connexion's request validator answered with an empty `message` and a `details` that was a *string*; 404, 405 and 413 came out as RFC-7807 problem documents; and the API-key check answered `{"error": "unauthorized"}`. Three of those were undeclared, so a client had to be able to parse all four. Everything now answers in the declared shape, `details` is always an object, and the validator's own text ("'text' is a required property") is in `message` where clients look for it. Getting there meant claiming every status code Connexion claims, because Connexion registers its handlers per status code and Flask prefers those over a handler registered for the `HTTPException` class. Nothing a caller can act on was dropped: which field is missing, which label sizes exist, that `copies` exceeded its maximum, and the printer's own words when a print failed all read exactly as before.
- **The gate says what it released the job on.** The pause before the first print attempt announced "The printer reports itself ready" in every case, although the gate also releases a job on a printer that answers steadily for 20 s without ever saying so — no IPP, or a blocking condition reported while booting. The queue could not tell the two apart because the gate handed back an attempt schedule and nothing else; it now hands back the sentence with it and the queue prints it verbatim, so a printer that has not reported readiness says so ("The printer is answering but has not reported itself ready. Giving it 5s before printing anyway."). Neither side has to learn the other's vocabulary, and a gate with nothing to say gets wording that claims only what the queue can see for itself.
- **The Docker image no longer carries a build toolchain, and its code is not writable by the app.** `build-essential`, `libffi-dev` and `libssl-dev` were installed to compile dependencies that do not need compiling: every requirement resolves to a wheel on amd64 and arm64, and the one source distribution, `packbits`, is pure Python. Dropping them takes the image from **770 MB to 334 MB** and its OS vulnerability count down to what `python:3.11-slim` brings on its own — a scanner counted 17 critical and 80 high before, 4 and 19 after. `chown -R appuser /app` is gone with them: the application code belongs to root and only `/app/data` and `/app/uploads` are writable by the runtime user, so a file-write bug in the upload or share handling cannot become code that survives a restart. `UPLOAD_FOLDER` is set explicitly in the image for that reason, since the old fallback pointed inside the code tree.
- **`docker-compose.yml` runs the container read-only, without capabilities and inside bounds.** `read_only: true` makes the ownership above structural rather than a matter of permissions being right, and the one place the process genuinely writes — gunicorn's worker heartbeat and the rendered-label scratch directory — moves to a 64 MB tmpfs mounted `noexec,nosuid`. Added with it: `cap_drop: ALL` (the app listens above 1024 and opens ordinary sockets, so it needs no Linux capability), `no-new-privileges` against the SUID binaries the base image still carries, and limits it has never come near — 512 MB against a measured ~75 MB, one CPU, 256 processes, the memory headroom sized to cover the largest image the app accepts before refusing it. One consequence to know: with `UPLOAD_FOLDER` on the tmpfs, **rendered labels and staged shares do not survive a restart**. They were never meant to — render, print, delete, plus a TTL sweep — and the job list has always lived in process memory. To keep them, point `UPLOAD_FOLDER` at a mounted path (`/app/uploads`) instead; the alternative is written out beside the setting.
- **A job prints into the boot window instead of waiting it out.** Measuring a cold start (`tools/boot_timeline.py`) produced the numbers this was missing: the first answer of any kind at 15.7 s, tcp/9100 at 17.1 s — and then the IPP port stops accepting at 23.4 s and comes back 1.4 s later, while ICMP and 9100 never falter. Nothing drops off the network; the print service rebinds the port partway through the boot, taking out exactly the thing readiness is read from. A printer saying "ready" mid-boot can therefore mean it and then withdraw it. Waiting out the worst case made every good cold start pay for the bad one, and no length of wait proves a printer will accept a raster — trying does. So the gate now releases the job on the printer's own "ready" and the job is **tried three times, at 5 s, then 20 s, then 20 s**; only the third failure is the job's failure, and it carries the printer's own words. Between attempts the job goes back to `queued` with the activity `retrying`: it is not on the wire and stays cancellable, and a cancel lands within a quarter second. A printer that was already up gets exactly one attempt, because a wrong label size should not be tried three times before it is reported. The one wait that survives is for a printer that answers without stating readiness (no IPP, or a blocker reported while booting): 20 s of continuous answering stands in for it, with probing tightened to 1 s once anything answers, since a 1.4 s hole is invisible to a probe every 2 s. Two things end the schedule early: the printer was already written to — a failure after bytes went out may mean part of the job printed, and repeating it would print that part twice — or the queue was paused or stopped, in which case the job fails carrying the printer's own last error rather than being left queued for a worker that has moved on.
- **The relay gate leaves the printer alone before looking at it, and waits far longer overall.** An unanswered reachability probe costs 3.5 s, so a loop that slept three seconds between probes really ran every 6.5 s, and the first probe landed six seconds after mains-on, into a window where nothing can answer. The gate now waits 20 s after the `turn_on` webhook before looking at all, then probes for up to 120 s; if the printer is still not there a second `turn_on` goes out with a 20 s + 60 s budget, for the case where the first request was accepted but not acted on. Worst case is about 220 s before a job fails, up from 75 s, and the failure names the webhooks delivered, the blind wait, and how many probes were made over what period. Everything is a ceiling: a printer ready at thirty seconds prints at thirty-eight, and one already awake waits not at all.
- **The relay's timing chain is reported as clock times, not offsets.** Each of the four moments — where the chain starts, the end of the keep-alive heartbeat, the printer's own power-off, and the `turn_off` webhook — now carries an absolute timestamp, an ISO-8601 form and its own seconds-until, all read off a single `server_time`, so a countdown can be anchored per moment and ticked locally without drifting. `next_step` names the moment the chain is waiting on, answered by the server because the hard part is which steps exist at all rather than which timestamp is smallest. `origin_source` says what the origin really is — a print, the process start before the first print, or an idle re-base — and `last_print_at` carries the real last print and is null when there has not been one, so nothing displays a print that never happened. The step that can cut mains power is never projected: `scheduled_turn_off_at` carries a time only once it has actually been armed, and an armed moment already overdue is reported as it stands. `hardware_offset_applied` and `printer_power_off_seconds` settle what the numbers alone could not: with the feature off, the effective window equals the configured one, which is indistinguishable from subtracting zero.
- **The interface's own assets are served by the app instead of fetched from a CDN.** This app drives a label printer on a local network, and such a network may have no route out: Bootstrap's stylesheet and bundle, the icon font, the two web fonts and the QR code library were all being fetched at load time. The stylesheets failing is visible and survivable; the bundle failing is not — without it there are no tabs, dialogs or dropdowns, eleven hidden elements become visible and the queue claims to be paused, with no console error, so the interface looks fine and does nothing. Everything now lives in `src/static/vendor` with versions and licences recorded there. The web fonts carry the latin and latin-ext subsets only.
- The webhook result line in the relay panel is composed from the response's own fields ("turn_on delivered. HTTP 200, mains power on.") instead of printing the server's whole sentence, which opened by repeating the URL from the field above it; the server's full text moved behind a toggle rather than being discarded. The two action columns share a structure — body, button, result — so buttons and results line up.
- Reworked the web UI into a "Console" layout: sidebar navigation, light/dark themes that follow the system preference, a fully responsive and iOS-friendly experience, and Settings as its own dedicated view.
- **Notices no longer carry a coloured bar down their left edge.** Severity now sits on the notice's icon, which the toasts already had and the calibration status line did not, so there is one card style instead of four nearly identical ones. Amber gained a colour of its own so a warning stays legible on a dark panel, as green and red already were.
- Invalid input now returns HTTP 400 (instead of 500), and image uploads are hardened.
- Expanded documentation for settings, environment variables and API endpoints.
- **The README has been rewritten.** It had grown to 762 lines and still showed an interface that has since been rebuilt. It is now a third of that, ordered by what somebody needs in order to decide whether to run this, with every setting and its default listed, current screenshots, and a table of the printers and media actually printed on.
- **Python 3.11 is now the minimum** (was 3.9, which reached end of life in October 2025). The Docker image moves to `python:3.11-slim`. Running from source on 3.9 or 3.10 is no longer supported. This also unblocks current Pillow, urllib3 and requests releases.
- Dependencies: Pillow 10.4.0 → 12.3.0, flask-cors 4.0.0 → 6.0.5, gunicorn 21.2.0 → 23.0.0. `marshmallow`, `pydantic` and `python-dotenv` were unused and have been dropped; `pytest`/`pytest-cov` moved to `requirements-dev.txt` so test tooling stays out of the runtime image.

### Removed
- **The SNMP code, and the two dependencies behind it.** `_snmp_ping` and `get_printer_clock` had no callers — not in Python, not through an `operationId`, not from the frontend. **The printer clock is unaffected**: it never came from there. `get_printer_clock` was the never-wired twin of `_build_clock_info`, and it is `_build_clock_info` that feeds the status response and `/health/printer`, unchanged. `_snmp_ping` was the only consumer of `pysnmp`, which drags in `pyasn1`, `pysmi`, `pycryptodomex` and `lark`; all of it is gone from `requirements.txt` and `setup.py`, and with it four of the twelve pip-audit exemptions (all `pyasn1`). The keep-alive it was written for has used the raw port and IPP for a long time. The remaining exemptions are the connexion 2 pin holding Flask at 2.2.5 and Werkzeug at 2.2.3, and they stay until that migration happens.
- **The P-touch tape sizes (`pt12`, `pt18`, `pt24`, `pt36`) are no longer offered.** They are TZe cassettes for Brother's P-touch machines, not DK rolls: no QL printer can take one mechanically, and this app has only ever offered QL models to print with. Selecting one could never produce a label, so the four entries have been dropped from the label list and from the API's `label_size` enum. Nothing else changes: the printing library still knows them, and no supported medium is affected.

### Security
- **Two limits on what a single upload may cost the app**, both previously reachable without authentication. A PDF was rendered page by page into a list before anything printed and only the *preview* capped how many, so a 40-page document went through on the print path; the count is now checked once the page range is parsed and before a single page is rasterised, and it measures the **selection** rather than the document, because printing three pages of a 200-page manual is a reasonable thing to ask for. An image of 100 megapixels passed inspection because Pillow's own guard warns at its limit and only raises at twice it — an 8000 × 8000 PNG of 79 KB was decoded in full — so the pixel count is now read from the header before any decode. Both carry a default and are overridable per installation: `MAX_PDF_PAGES` at 20, `MAX_UPLOAD_IMAGE_PIXELS` at 50 000 000, with an explicit `0` meaning no limit at all. Anything unparseable falls back to the default rather than to no protection, because a blank variable in a compose file means "not configured", not "let everything through". The refusal names the limit and the value that broke it, in `message` and in `details`, so it can be acted on without reading the source. One asymmetry worth knowing: `POST /image/preview` refuses immediately with HTTP 400, while the print endpoints enqueue before the service sees the file, so there the same message arrives as a failed job. (The env var is deliberately not called `MAX_IMAGE_PIXELS`: that name belongs to Pillow's own attribute with different semantics, and the collision is the blind spot the file slipped through.)
- **Internals no longer travel in error responses.** Twenty-three controller paths ended in `except Exception` wrapped into `PrinterError(f"...{str(e)}")`, which both mislabelled a bug in the app as a fault of the printer and copied the raw exception text into the HTTP response, going round the generic handler that exists to prevent exactly that. They now log the whole story — message, exception type, stack trace and a correlation id — and answer "An internal error occurred" plus `details.error_id`, which is enough to find the log line and nothing else. Absolute server paths are redacted centrally on the way out, which covers messages the app does not write itself (the PDF renderer put the path of the temporary upload into a 400). Writing this turned up a case where an actionable message had already been lost — a `PrinterError` raised inside the status check was being swallowed into a generic 500 — so domain errors are now re-raised past the generic clause instead of falling into it.
- **The container runs read-only, unprivileged and bounded**, and the image no longer ships a compiler, apt-installable build tooling or code its own user can write. See the two entries under Changed.
- Optional API-key authentication via the `API_KEY` env var (every `/api/v1/*` request then needs `X-API-Key`; the API stays open when it is unset); configurable cross-origin access via `CORS_ORIGINS`, same-origin only when unset; printer-URI scheme allowlist with an SSRF guard; path-traversal protection on served job/share files; image decompression-bomb limit.

### Fixed
- **A finished job stops being described, and a job the worker still holds counts as work.** The pre-job gate is a plain callable that does not know which job it is holding and cannot be interrupted, so it went on writing activities onto jobs that had been cancelled a minute earlier. `GET /jobs/queue` then answered "nothing is queued, nothing is printing, and here is what is currently happening" in the same breath — and the guard that holds the relay open while work is pending read that as no work, so a turn-off falling due while the gate was booting a printer would have cut mains mid-boot. Terminal jobs now refuse activities (clearing one is still allowed, since that is how the worker tidies up), the queue reports none for them, and pending work counts the job still in the worker's hands, so the relay stays open exactly as long as the gate is running.
- **The Threshold slider reaches the client-side preview.** It dithered against a fixed midpoint of 128 while the server computes the cutoff from the setting — 76.5 at the default of 70 — so the instant preview showed a label the printer would not produce, and moving the slider changed nothing visible. It now uses the server's own formula, `(100 - threshold) * 255 / 100`, over ITU-R 601 luma rather than a flat average of the three channels (on pure red the two differ by 85 against 76, enough to land on opposite sides of the cutoff). Dithering keeps the fixed midpoint on purpose: Pillow's one-bit conversion has no threshold to give it.
- **Server text is escaped before it is displayed.** Notifications built their message into `innerHTML` and are fed with server error text and warnings; the printer status line did the same with the device's own words, sitting in the same template beside a media line that escaped its own data. Both go in as text now, while the frame, the icon and the close button stay markup.
- **"Open" works on a Text+Image job**, which was offered the button and could not use it because the handler did not know the type — file and all. A calibration job has no compose form to open and never will (it is generated from the settings dialog; Reprint is the operation that makes sense for it), so its button says why instead of failing when pressed, and keeps its place so the action bar does not change shape from row to row.
- **The interface declares a favicon**, drawn inline as an SVG data URI, which ends the `/favicon.ico` 404 on every single page load — the only error in an otherwise clean console, and the kind of noise that trains people to stop reading it.
- **The header's activity stopwatch is hidden from screen readers** and its poll stands down in a hidden tab, as the queue panel's own poll always has. It sat inside a live region and was rewritten on every poll, which turned one four-minute boot into some fifty identical announcements; what changes for a screen reader is the phase, and the phase alone stays announceable.
- **A QR code is captioned with what it encodes when no text was typed.** Ticking "Show text with QR code" and leaving the field empty printed no caption at all, although the render path has always defaulted the caption to the QR data: the controllers never let it get that far, because the whole text block — including `show_text` itself — sat inside "if the caller supplied text". Only the caption is conditional now. The quick client-side preview had been drawing the caption all along, so it showed something neither the server preview nor the print produced; the three agree again. The combined text+QR label is deliberately left alone: there the text is the label's content rather than a caption, and empty really is an error.
- **An odd printer clock no longer fails the whole status check.** `POST /printers/status` returned 500 with `'str' object has no attribute 'isoformat'` for a printer that sometimes answers `printer-current-time` with something other than a datetime. The clock is a readout beside the status, not part of it: a string that parses is used, one that does not is shown as it came with a note, and a value that is not a time at all is treated the same way instead of raised. A reading without a timezone gets its own note and no drift figure, since comparing the printer's local time to UTC would invent a drift of exactly the timezone offset.
- **Real relay responses are no longer rejected by the specification.** Firing a webhook by hand returned HTTP 500 and "Response body does not conform to specification" although the relay had answered 200: the mains-power enum was written as `enum: [on, off, unknown]`, and YAML reads bare `on` and `off` as booleans, so the schema validated against `[true, false, "unknown"]` while the service correctly returned the string `"on"`. The values are quoted now.
- **Upload settings are held to the same rules as a JSON request's.** A file upload carries its settings as a string in a form field, which is all the specification can describe, so everything inside it went unchecked and the two ways of printing the same label disagreed: `copies: 101` was a 400 on `/text/print` and a queued job on `/image/print` that failed in the worker later. The four multipart endpoints now validate the parsed object against the same `PrintSettings` schema, read from `openapi.yaml` at first use rather than copied into Python. Keys the schema does not name still pass, because layout hints ride along there.
- **A confirmation raised from inside a dialog is reachable.** Every Bootstrap modal has the same z-index, so the mains-power confirmation opened behind the dialog that raised it: the question was readable, its buttons were not, and the outer modal swallowed every click aimed at the inner one. A confirmation now lifts itself above the highest open modal and drops its backdrop between the two, and the page stays locked when the inner dialog closes. Destructive confirmations (cutting mains power, stopping the queue, clearing every job) gained a hazard icon, a red confirm button and focus on Cancel, so a reflexive Enter cannot cut power.
- **A failed write no longer leaves the socket open.** `backend.dispose()` moved into a `finally`; the printer accepts one connection on port 9100 at a time, so the leak landed exactly where the next attempt was about to reconnect.
- **Labels are rendered at the loaded roll's real printable width** instead of a hardcoded 696 px (62 mm). Narrower media was previously drawn too wide and rescaled on the way to the printer, so the requested font size never matched what came out: on 50 mm tape everything printed about 20% small and soft. Affects text, images, PDF pages and the combined text+QR and text+image layouts (reported and diagnosed by [MSanteler](https://github.com/MSanteler) in [#18](https://github.com/dodoooh/brother_ql_app/pull/18)).
- **Text on die-cut labels works at all.** The canvas is now pinned to the label's fixed physical height, which `brother_ql` requires; before, any other height was rejected outright.
- **Die-cut labels work for every kind of content, not just plain text.** Images, PDF pages, QR codes and both combined layouts (text+QR, text+image) were rejected outright on die-cut media, because `brother_ql` requires a die-cut image to be exactly the label's own size and only the plain-text path produced one. A QR code was always sent at its own configured size and came back as "Bad image dimensions". Every content type is now centre-fitted onto the label's exact canvas. Affects round and rectangular die-cut media alike.
- **Images on round labels are no longer a third smaller than they could be.** The fit measured the image's rectangle, and a square only fits inside a circle at about 71% of its width, so every picture was shrunk by that much whatever it contained: a design drawn to the edge of a 24 mm round label printed at 13 mm, ringed by bare paper. Round media now measures the ink instead, so artwork that is itself round, or simply has empty corners, fills the label: the same design now prints at 19 mm. A photograph with ink in its corners is unchanged, because there the rectangle really is the content — as it is for QR codes, whose quiet zone is part of the symbol and is deliberately left alone.
- **Round labels (`d12`, `d24`, `d58`) are laid out to the circle instead of the square around it.** The printable area of a round label is a circle, but the raster is its bounding square, so anything near the corners used to be printed onto the backing paper and lost. Text is now measured against the width actually available at each line's own height, which keeps a single centred line close to the full diameter. Fitting everything into the largest square inside the circle would have cost about a third of the font size for nothing. Images and QR codes are fitted so they sit inside the circle, and a small rim margin absorbs the tolerance of the die cut.
- **Text on die-cut labels is centred vertically** instead of starting near the top edge, which on a round label is the narrowest part of the medium.
- **Words are no longer broken in the middle on die-cut labels.** `auto_fit` only tested whether the text block fit the label, and chopping a word in half satisfies that just as well as shrinking the font does: "Kalibriert 2026" on a 24 mm round label came out as "Kalibrier" / "t 2026" at the default font size, although it fits on one unbroken line two steps down. Die-cut media now reduces the font until whole words fit, the same rule continuous tape already followed. Rectangular die-cut labels such as `62x29` had the same fault.
- **Combined text+image labels no longer fail on narrow media.** The layout reserved a fixed padding that exceeded the printable width below about 120 px, leaving no room for the image column and raising an error. This broke `d12` and 12 mm continuous tape alike. The padding now scales with the label; nothing changes at 24 mm and above.
- **Rotation now has an effect.** The image was rotated once by the app and a second time by `brother_ql`, which returned it to its original orientation: the log said "Rotation applied" and the label came out unrotated. Image and PDF prints also rotate before being fitted to the label, instead of after, which used to leave them narrower than the tape and scaled back up.
- Descenders on the last line are no longer clipped: line height is measured from the font's ascent+descent rather than the ink bounding box, which only covers the glyphs actually present.
- Text on narrow continuous rolls no longer degrades into a column of single letters. With the true width in play, a word can be wider than a 12 mm label; the new `auto_fit` setting (on by default) shrinks the font until every word fits a line instead of hard-breaking it. On die-cut labels it shrinks to the fixed height instead. Disable per request with `settings.auto_fit: false`.
- **`QL-1100NWB` was never a real model.** It was offered in the printer dropdown and accepted by the API, but `brother_ql` has no such model, so choosing it failed at print time. The actual device is the **QL-1110NWB**, which was missing; it and the **QL-600** are now offered instead. The printer list in the UI and in the API specification is once again exactly the set the printing library supports.
- Keep-alive now writes to the printer's raw port (`9100`) instead of only reading status, so it can actually prevent the auto power-off on network printers.
